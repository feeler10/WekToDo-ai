# WekToDo-ai v0.1.2 查询理解与澄清闭环设计

## 版本目标与阶段边界

v0.1.2 的整体目标是形成“结构化查询语义、确定性条件校验、跨轮补全、确定性查询计划、Redis 真实查询、可插拔任务匹配、中文响应”的任务查询闭环。实现按三个阶段推进：

1. 阶段一只实现查询语义契约、确定性查询完整性校验、意图 Prompt、Fake Provider 支持和相关测试。
2. 阶段二实现 `TaskQueryPlan`、Redis 组合查询及可插拔 `TaskMatcher`/`KeywordTaskMatcher`。
3. 阶段三实现 Checkpoint 跨轮补全、候选消歧状态、确定性中文响应和能力边界。

当前代码已完成阶段一和阶段二。阶段二只实现确定性查询计划、Redis 组合过滤和可插拔关键词任务匹配；阶段三的跨轮补全、候选选择和中文响应仍只保留冻结设计。

## 当前架构适配

仓库已有独立的 `app/intent/` 模块，因此 `TimeScope`、`ClarificationReason`、`TaskQueryIntent` 和扩展后的 `IntentResult` 继续放在现有意图模块，不新增职责重复的 `schemas/query_intent.py`。现有 `TaskStatus`、`TaskPriority` 由 `app/schemas/task.py` 统一定义并直接复用。

阶段一的确定性完整性校验位于 `IntentRecognitionService` 与 Graph 路由之间：Provider 负责给出经过 Pydantic 结构校验的 `IntentResult`，确定性代码重新计算查询是否需要澄清，Graph 只消费校验后的结果。阶段二的查询 Graph 直接消费该结构并构造 `TaskQueryPlan`，不再从用户原句重复提取时间、状态或优先级；旧 `parse_task_query()` 只为现有兼容调用保留，不参与生产查询链路。

## 查询语义契约

`TimeScope` 的冻结值如下：

- `TODAY`：当前业务时区的今天。
- `TOMORROW`：当前业务时区的明天。
- `THIS_WEEK`：当前业务时区本周，周一为一周开始。
- `OVERDUE`：截止时间早于当前时刻且状态未终止。
- `ALL`：用户明确要求所有时间范围，不是缺省回退。
- `CUSTOM`：用户明确给出自定义起止时间。
- `UNSPECIFIED`：用户没有给出时间范围。

`TaskQueryIntent` 保存 `time_scope`、`statuses`、`priorities`、`start_at`、`end_at` 和 `raw_time_expression`。状态和优先级使用集合语义；所有非空时间必须带时区，完整区间必须满足 `start_at < end_at`。原始时间表达仅用于诊断、澄清和测试，不直接作为 Repository 查询条件。

`IntentResult` 保留 `intent`、`confidence`、`reason`、`task_reference`、`target_status`、`needs_clarification` 和 `clarification_question`，新增 `query` 与 `clarification_reason`。只有 `QUERY_TASKS` 可以携带 `query`；查询状态只能放入 `query.statuses`，查询不得携带 `target_status`。状态更新继续使用 `target_status`，其确认机制不变。

## 通用时间区间约定

`TimeScope` 是常用快捷语义，不穷举所有自然语言时间。固定的“今天”“明天”“本周”“所有时间”和“逾期”继续分别使用 `TODAY`、`TOMORROW`、`THIS_WEEK`、`ALL`、`OVERDUE`，并且不携带 `start_at` 或 `end_at`。固定范围的真实边界留给阶段二的确定性查询计划计算。

其他语义明确的时间表达，例如“昨天”“前天”“昨天的昨天”“未来三天”“过去三个完整自然日”“下周二到下周五”“上个月”和明确日期区间，统一使用 `CUSTOM`，由 LLM 基于注入的当前日期时间和业务时区输出带时区的 `start_at`、`end_at`，同时在 `raw_time_expression` 中保留原始文本。本阶段仍依赖 LLM 完成复杂自然语言时间解析，不新增确定性相对日期解析器或第三方日期库。

所有时间区间统一采用左闭右开语义 `start_at <= due_at < end_at`。自然日结束使用下一自然日 `00:00:00`，不使用 `23:59:59`。产品约定“未来三天”包含今天在内的三个自然日；“上午”为 `[00:00,12:00)`，“下午”为 `[12:00,18:00)`。

`ALL` 表示用户明确选择所有时间，不需要澄清；`UNSPECIFIED` 表示用户没有提供时间，列表查询必须追问。`OVERDUE` 是需要结合 `due_at < now` 和非终止状态判断的特殊语义，不等价于普通截止到当前时刻的区间。

“前三天”“这几天”“最近一阵子”“月底前后”“过几天”等明显存在多种解释的表达不得猜测。模型应保留原始表达并返回 `AMBIGUOUS_TIME_EXPRESSION`；`CUSTOM` 缺少端点时由后端确定性改写为 `INVALID_TIME_RANGE`。所有模型时间输出仍须经过 Pydantic 时区、区间顺序和固定范围冲突校验，以及查询完整性复核。

## 查询完整性规则

确定性校验不信任模型给出的 `needs_clarification`，统一应用以下规则：

1. 存在具体、非空且非指代性的 `task_reference` 时，允许直接查询具体任务，不强制要求时间范围。
2. “那个任务”“这个任务”“它”等引用在没有已恢复上下文时视为缺少任务引用，设置 `MISSING_TASK_REFERENCE` 并追问任务名称。
3. 列表查询没有 `query` 时补为 `time_scope=UNSPECIFIED` 的查询语义，再按缺失时间处理。
4. 列表查询的 `time_scope=UNSPECIFIED` 时设置 `MISSING_TIME_SCOPE`。不得默认为 `ALL`。
5. `time_scope=CUSTOM` 但缺少 `start_at` 或 `end_at` 时设置 `INVALID_TIME_RANGE`；明显存在多种解释的时间表达设置 `AMBIGUOUS_TIME_EXPRESSION`。
6. `TODAY`、`TOMORROW`、`THIS_WEEK`、`OVERDUE`、`ALL`，以及字段完整的 `CUSTOM` 查询不需要澄清。
7. 未完成状态集合固定为 `TODO`、`DOING`、`BLOCKED`；已完成查询使用 `DONE`；高优先级查询使用 `HIGH`、`URGENT`。
8. `confidence` 只用于诊断，不得绕过任何结构校验、完整性校验、用户隔离、写确认或后续任务匹配校验。

阶段一只生成澄清结果，不保存跨轮状态。保存与恢复 `PendingQueryClarification` 属于阶段三。

## 阶段二查询计划与时间执行设计

阶段二由确定性 `TaskQueryPlan` 把 `IntentResult` / `TaskQueryIntent` 中的语义转换为可执行仓储条件。计划携带 `user_id`、`time_scope`、`task_reference`、状态、优先级及 `due_from`、`due_to`、`overdue_before`。意图层只表达用户语义；查询计划层只生成标准化边界；Repository 不接收也不解析 `raw_time_expression`。

固定时间范围使用请求业务时区和带时区 `datetime` 确定性计算：`TODAY` 为本地今天零点到明天零点，`TOMORROW` 为明天零点到后天零点，`THIS_WEEK` 为本周一零点到下周一零点。边界通过本地日期分别构造，避免假设每个自然日固定为 24 小时。`CUSTOM` 原样消费阶段一已经验证的 `start_at`、`end_at`，不重新解释原始消息或 `raw_time_expression`。所有普通范围统一使用左闭右开语义。

`ALL` 不增加时间过滤；`UNSPECIFIED` 不得构造可执行计划；`OVERDUE` 使用 `overdue_before=now`，并在 Repository 中同时排除 `DONE`、`CANCELLED` 等终止状态。用户显式状态条件继续与逾期条件取交集，不能覆盖终止状态排除规则。

具体任务查询仍兼容阶段一“有有效 `task_reference` 时不强制时间范围”的规则：此时 `UNSPECIFIED` 不会被转换成计划或默认为 `ALL`，查询节点只从当前用户任务集合中执行 `TaskMatcher`。如果具体任务查询同时携带固定或 `CUSTOM` 时间范围，则先执行计划过滤，再在过滤结果中匹配任务引用。

当前任务模型和 Redis Repository 使用字段名 `deadline`。Redis 通过 `Task.model_dump_json()` 保存带 UTC offset 的 ISO datetime，没有强制把原偏移改写为 UTC；读取时由 Pydantic 恢复为 aware datetime，Python 按绝对时刻比较不同偏移。为兼容现有存储契约，`TaskQueryPlan.due_from/due_to` 映射为 `TaskQuery.deadline_from/deadline_to`，不新增第二套日期存储标准。Repository 从当前 `user_id` 的专属任务索引取数后，组合应用时间、状态和优先级，并对截止时间执行 `deadline >= deadline_from`、`deadline < deadline_to`。

任务存在性、状态、进度、截止时间和优先级只来自 Redis 中的真实 `Task`，不由 LLM 生成。查询只读且不创建 `PendingAction`；状态更新唯一匹配后仍进入现有确认链路，确认前不得修改 Redis。

## 阶段二 TaskMatcher 设计

上层 Graph 和领域服务只依赖统一 `TaskMatcher` 抽象。阶段二的默认实现为 `KeywordTaskMatcher`，匹配顺序冻结为：精确任务 ID、精确标题、规范化标题、标题关键词包含。空引用不得成为通配符；零候选、唯一候选和多候选使用统一结果契约；多个候选必须由用户选择，不自动选第一个或最高分。

标题规范化只允许可解释的空白、大小写和少量任务口语后缀处理。当前版本不做同义词、拼音、编辑距离、LLM 改写或语义扩展。未来可通过相同抽象接入 `VectorTaskMatcher` 或 `HybridTaskMatcher`，而不修改 Graph 主链路；本轮不创建这两个 Provider 的代码或空实现。

## 阶段三：查询上下文恢复、多候选交互与确定性响应

阶段三复用现有 LangGraph State 和 Redis Checkpointer，不创建第二套会话存储。Graph State 新增 `PendingQueryClarification` 和 `PendingTaskSelection`：两者均绑定当前 `user_id`、`thread_id`，保存 aware `created_at`/`expires_at`，并使用统一配置的短期过期时长。它们是可恢复的短期流程状态，不是任务事实、长期记忆或跨线程记忆。

`PendingQueryClarification` 保存经过结构校验的原始 `IntentResult`、确定性澄清原因及缺失字段。后续输入先转换为不带默认值的 `TaskQueryIntentPatch`，再由独立合并函数按字段合并；未提供字段保留原值，时间范围切换时统一清理冲突端点，`raw_time_expression` 只随时间补丁变化。合并结果必须重新运行阶段一 `validate_query_completeness()`，不能信任 Checkpoint 中旧的 `confidence`、`needs_clarification` 或问题文案。补全成功后仍使用阶段二的 `TaskQueryPlan` 和 Repository 查询。

`PendingTaskSelection` 只保存稳定排序后的候选任务 ID、候选版本及继续操作所需的最小上下文：查询操作可保存 `TaskQueryPlan`，状态更新操作保存 `target_status`。用户可用合法序号、候选 ID、精确标题或规范化精确标题选择，但选择范围不能扩展到候选集合之外。每轮选择前按当前 `user_id + task_id` 重新读取 Redis；Checkpoint 中的标题、状态、截止时间、优先级、版本和归属都不是最终事实。查询选择只返回真实任务详情，不创建 `PendingAction`；状态更新选择在重新校验存在性、版本和状态流转后，才进入现有确认链路，选择本身不等于确认。

同一线程的处理优先级冻结为 `PendingAction`、`PendingTaskSelection`、`PendingQueryClarification`、普通 IntentRecognition。`PendingAction` 继续由现有 interrupt/resume 机制独占处理；发现低优先级 pending 状态冲突时记录诊断并清理低优先级状态。查询补全或候选选择成功、用户取消、明确新请求替换、状态过期、候选全部失效或不可恢复一致性错误时清理相应状态；无效序号、仍然不完整的补丁或仍有有效候选时保留状态。过期输入按普通新请求处理，不执行旧流程。

中文响应由确定性格式化层基于真实 `Task`、`TaskQueryPlan`、候选和领域结果生成，不查询 Redis、不解析自然语言时间、不调用 LLM。状态和优先级中文映射集中维护；截止时间只在展示时转换到请求业务时区。列表数量、高优先级统计和顺序必须与真实数组一致；缺失截止时间等字段自然省略；零匹配不推荐相似任务；多匹配只展示当前有效候选并要求明确选择。`ALL`、`UNSPECIFIED` 与 `OVERDUE` 的响应语义继续保持阶段一、二的区别。

## 能力边界与明确不支持内容

v0.1.2 只处理任务管理范围。天气、新闻、网络搜索等请求不调用外部工具。当前版本明确不实现：

- `VectorTaskMatcher`、`HybridTaskMatcher` 的实际逻辑；
- 向量数据库、Milvus、Qdrant、Embedding 和语义相似度检索；
- 同义词召回、编辑距离推荐、拼音检索和相似任务推荐；
- 任务拆解业务、任务属性更新业务和多意图拆分；
- 长期记忆、跨线程记忆和完整代词消解；
- 每日简报、动态重新规划、SSE、复杂前端及外部 Trace 平台。

## 测试范围与验收标准

阶段一测试覆盖查询模型时区约束、查询与写操作字段边界、今天/未指定时间/全部/具体任务/缺少任务引用、高置信度错误输出的确定性纠正，以及 Fake Provider 新字段构造。pytest 不调用真实模型。

阶段二增加查询计划、跨时区自然日边界、Repository 组合过滤、Matcher 抽象、关键词匹配、查询只读边界和状态更新确认回归测试；阶段三增加跨轮 Checkpoint、候选选择、候选重读与重校验、确定性中文响应、能力边界和 E2E 测试。每阶段先运行局部测试，再运行完整回归并检查 Git diff。所有原有测试必须继续通过，且不得修改现有状态更新确认、幂等或用户隔离约束。
